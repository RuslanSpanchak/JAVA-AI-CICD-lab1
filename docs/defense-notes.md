# Короткі нотатки для захисту

## Варіант короткої усної відповіді

Мета моєї лабораторної роботи — спроєктувати AI-агента, який допомагає автоматизувати базовий цикл розробки та CI/CD. Я обрав Java, Maven і JUnit. Для прикладу реалізував консольний аналізатор тексту, який рахує слова, Unicode-символи та рядки.

Файл `build-engineer.agent.md` виконує роль manifest: задає роль агента, правила безпеки, інструменти та критерії завершення. Повторювані задачі винесені в три skills: створення структури, збірка з тестуванням і налаштування GitHub Actions. Окремі prompt-файли є commands для запуску операцій, а `init.prompt.md` координує їх у визначеній послідовності та має зупиняти процес при помилці.

Maven використовується для керування залежностями, компіляції, тестування й пакування застосунку. JUnit 5 перевіряє звичайні та граничні сценарії. GitHub Actions запускає однакову команду `mvn clean verify` у матриці з Linux, Windows і macOS. Це дає змогу виявляти проблеми, які можуть не проявитися на одній операційній системі.

Окремо визначені обмеження безпеки: не передавати секрети AI, не виконувати руйнівні Git-операції й не заявляти про успіх без фактичного результату перевірки. Локальна перевірка і віддалений CI розглядаються як різні кроки: результат усіх трьох runner-ів потрібно підтвердити у вкладці Actions на GitHub.

## Типові запитання викладача

**Що таке manifest агента?**

Файл з описом ролі, відповідальності, дозволених інструментів, правил безпеки та критеріїв завершення агента.

**Чим skill відрізняється від command?**

Skill — повторно використовувана інструкція для конкретного класу задач. Command — явно запускаємий prompt, який просить агента виконати конкретну операцію.

**Для чого потрібен orchestrator?**

Він визначає послідовність етапів, перевіряє передумови, зупиняється на помилці й формує звіт замість того, щоб оголошувати успіх після неповного виконання.

**Чому JUnit-тести важливі, якщо є AI?**

Згенерований код може містити логічні помилки. Тести формалізують очікувану поведінку та дають відтворювану перевірку після змін.

**Навіщо тестувати на трьох ОС?**

Одна команда може поводитися по-різному через середовище, шляхи або налаштування. Матриця CI виконує однакову перевірку на Linux, Windows і macOS.

**Чи означає наявність `ci.yml`, що CI уже пройшов?**

Ні. Файл лише конфігурує workflow. Фактичний результат підтверджується запуском workflow у GitHub Actions.

**Що робить агент у разі помилки?**

Він повинен зупинити оркестрацію, показати реальний результат і причину, запропонувати мінімальне виправлення та повторити перевірку. Він не повинен приховувати збій або пропускати тести.
